Purpose
-------
Compare native pyflow_acdc loss-minimization OPF with the legacy ACDCPF-backed Stagg 5-bus OPF settings.
This is a numerical sanity comparison, not proof that the two formulations are identical.

Runs
----
1. Base pyflow PF: pyflow_acdc.ACDC_sequential on Stagg5MATACDC.
2. Native pyflow OPF: pyflow_acdc.ACDC_OPF.Optimal_PF with ObjRule={'AC_losses':1,'DC_losses':1,'Converter_Losses':1}, OnlyGen=False.
3. Tool1 (acdcopf) legacy run: acdcpf_opf Stagg 5 script settings at the time of this report, ACDCPF-backed SLSQP, converter[0,2] P_AC and Q_AC only.

Important comparability note
----------------------------
The native pyflow OPF is allowed to move a wider set of variables. In this run it redispatches AC generators strongly.
The Tool1 (acdcopf) legacy Stagg 5 setup intentionally keeps non-slack AC generator active dispatch fixed, to avoid reducing losses by simply moving generation.
Therefore lower pyflow losses do not automatically mean Tool1 (acdcopf) is wrong; it is solving a more restricted control problem.

Main interpretation
-------------------
- Pyflow OPF reaches much lower losses mainly because it redispatches generator active power: gen 1 rises from 40 MW to about 155.8 MW.
- Our current OPF keeps generator active dispatch fixed and only moves selected VSC P/Q setpoints, so the loss improvement is intentionally small.
- The pyflow and ACDCPF base PF totals are close but not identical; converter loss reporting/model details differ by about 0.1 MW in this case.
- A fair one-to-one benchmark should align the allowed controls and the converter/slack conventions before comparing objective values as if they were the same problem.

Recommended next validation
---------------------------

2. Run both solvers with the same allowed controls and fixed setpoints.
3. Compare final PF validation outputs, not only optimizer objective values.
